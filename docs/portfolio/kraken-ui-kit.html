Kraken UI Kit: a design system AI assistants can look things up in, and new brands plug into

How do you make a family of internal apps feel like one product, when AI is writing a growing share of the screens?

Problem

AI assistants make things up and type raw colors and numbers straight into the code, so JIT's internal apps stop matching the design and each other. I wanted one system that keeps every screen on brand, whether a person or a machine builds it.

Solution

Kraken UI Kit is a fully tokenized design system. Every color, size and font is a design token in one source of truth, designers edit the tokens in Figma, and skills keep the code, the documentation and the AI assistants in sync.

Users

Designers and developers building JIT's internal apps, the AI assistants working next to them, and teams on client projects that have no design system of their own. Behind them, the people who use those apps every day.

Result

In a test, an assistant connected to the kit built an on-brand delete dialog from one casual prompt, in both brands, with no hardcoded color. It is one test, not a study.

TL;DR

JIT's internal apps needed to feel like one product, and AI assistants kept making things up and hardcoding values, so screens drifted away from the design. I built a design system where the tokens are the source of truth, Figma is where designers edit them, and assistants look facts up instead of guessing. In one test, a casual prompt produced an on-brand dialog in both brands.

Context

JIT's internal apps grew over many years, and they were built on different technologies. Each one looks and behaves a little differently, and there is no shared source of truth, so maintaining them is hard.

Now all of them are moving into one place. Side by side, every difference is something the user has to learn again. We wanted one visual language and one set of behaviors, so no app overloads its users and nobody has to learn each one from scratch.

The same need showed up outside the company. We take on small, fixed-term projects for clients that have no design system of their own, and each one meant a new brand to set up and screens to build fast. We wanted a universal toolkit: a quick way to add a new theme, and tools that make building the screens smooth.

Then AI assistants started writing real screens. They are fast, and they are confident. Ask for a settings page and you get a good-looking one in a minute that belongs to no brand.

The problem

An AI assistant without a design system invents one, and nothing in our setup stopped it. It made up button styles and names, and it hardcoded values: a raw color or number typed straight into the code, instead of the one the design system defines. It did all of this with total confidence.

For the people using the apps, a difference in how a button looks or a dialog behaves is something to learn again. Each of those breaks the link between the design and what ships, so the apps and the design files stop matching. A person has to find and fix every discrepancy, and the faster the assistants get, the more there are to find.

Both dialogs say the same words in the same font. The left one has no close button, a warning triangle where the kit uses an info circle, and every button grouped on the right. None of it fails a glance, which is why a person still has to look.

Coherence across the internal apps was the goal. AI made it urgent. And client projects with no design system were the test of whether the answer was reusable: setting up a new brand had to be nearly frictionless.

What I noticed before building

  • A design decision is only real when it lives in exactly one place. Two editable copies of a color means the color has no owner.
  • An AI is most confident exactly when it is guessing. The fix is not better prose. It is giving it somewhere to look things up.
  • Documentation is only honest if it can fail. A wiki page goes stale silently. A playbook that gets run either works or breaks loudly.

What I decided

Decision one: the tokens are the source of truth, and Figma is where they get edited

The whole kit is tokenized. Every color, size, radius and font is a named value, called a design token, and the components contain no raw values at all. That rule is easy for a machine to check: a raw value is something you can search for and block.

The tokens live in a file in the W3C design token format, an open standard, not inside any one tool, because tokens should outlive the tools around them. Figma is the editor. Designers change tokens there using Figma variables, and a Claude skill pulls the changes into the token file. A build step then writes the stylesheet the components use. Nobody edits the stylesheet by hand.

One value, three places. A designer changes "primary" in Figma, a skill copies the change into the token file, and the build step carries it into every component that uses it. Nobody retypes the color along the way.

The tokens sit in three layers: the raw palette, the meaning ("primary"), and per-component settings. Only the meaning layer changes per brand. So a new brand is a new set of values in Figma and one playbook run, and the whole product switches with a single attribute. No screen changes and no component changes.

Only one setting differs between these two. That is what makes a new client brand quick: a new set of values, not a new set of screens.

The trade-offs were real. Nobody can "just quickly fix it in code" anymore, because every change goes through the tokens and a sync. Three layers also mean finding the real color behind a component takes two hops, which Storybook and the fact sheets now absorb. And a brand can change values but not the shape of a component. A client who wants a different button anatomy doesn't fit, and I scoped that out on purpose. Changes to shape are design decisions in Figma, not forks in code.

Decision two: let the kit answer questions instead of hoping it gets read

I didn't write more documentation. Every component publishes a fact sheet generated from the code: its exact options, defaults, colors and usage rules. A small connector lets any AI assistant look those facts up in the middle of a task. "Which button styles exist?" stopped being a memory test and became a lookup.

The assistant did not remember the button styles. It asked, and the kit answered with the real list. That is the difference between a lookup and a guess.

I built the kit to match shadcn, a popular open source set of interface parts that nearly every AI model has already seen. An assistant arrives with correct instincts and only has to learn our few differences, which are published as a short list. The first one is buttons. Our Figma set has a tonal style and two extra destructive styles that shadcn doesn't, and shadcn's link style isn't in ours, so I kept the Figma set and mapped the rest.

The trade-off: I gave up naming freedom, and I gave up elegant code. Each component file follows a rigid pattern so the facts can be read straight from it. I'd rather have a slightly awkward file than a fact sheet nobody can trust.

People get the same answers. Storybook, a living catalog of every component, mirrors the property panel of its Figma component one to one, so a designer can put the two side by side and check them.

A designer can check a component against its Figma version without reading any code. If a name or an option ever differs between the two panels, it shows in one glance.

Decision three: looks right is not right

Fact sheets tell an assistant what is true. Something still has to catch it when it ignores them. Every change rebuilds what is generated and compares it line by line with what is saved, so one drifted value turns the project red. That check once caught an automated cleanup pass that had quietly corrupted the fact sheets, and I fenced those tools off from the generated files.

But a check only catches what it knows to look for, so I also ran a review over every component against its Figma version and the rules of the kit. The rule I held hardest: a component that looks identical on screen still fails if it gets there with a raw value. A radio button's dot was hardcoded white. A switch's thumb was hardcoded white. A drawer's rounded corners resolved to the wrong radius. An accordion had a fixed pixel height. The assistants' output looked right and wasn't. Each one was a spot where the kit's promise, that nothing is hardcoded, could quietly break, so I sent each component back until it passed.

Recurring jobs became playbooks an assistant runs step by step: syncing tokens from Figma, adding a brand, auditing whether Figma and code still agree. A playbook either works or fails loudly. The cost is that playbooks take time to write and keep alive, and they only pay off if they get run again and again. I accepted that because the kit is meant to be reused for every new brand.

The outcome

The test that mattered: an empty project, an AI assistant connected to the kit, and one casual prompt, "build me a delete confirmation dialog". The assistant looked up the real component, used the correct destructive style, and produced a dialog that was on-brand in both brands, with no hardcoded color anywhere. It worked for two reasons. The assistant could look up the real component instead of guessing, and every color it used resolved through the tokens, so the dialog followed the brand switch.

That is one test, not a study, and it is the clearest proof I have that the lookup works.

Watch for two moments: the assistant looks the component up before it writes anything, and the brand switch at the end changes the dialog without anyone touching it. The final search finds no raw colors.

What I'd tell my past self

The audience of a design system now includes machines, and they need different things from people: facts they can look up, rules they can't misread, and a loud failure when something drifts. Designing for that changed what I count as good documentation.
