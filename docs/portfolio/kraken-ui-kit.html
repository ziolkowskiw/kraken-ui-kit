Kraken UI Kit: a design system AI assistants look things up in, instead of guessing

How do you make a family of internal apps feel like one product, when AI is writing a growing share of the screens?

Problem

JIT's internal apps already look and behave differently, client projects start with no design system at all, and AI assistants that guess make both worse.

Solution

Kraken UI Kit is a design system where designers edit the tokens in Figma and assistants look things up instead of guessing, so internal apps share one set of parts and a client project gets a new brand by changing values.

Users

JIT's designers and developers building internal apps and fixed-term client projects, and the AI assistants working beside them.

Result

In an empty project, an assistant connected to the kit built an on-brand delete dialog from one casual prompt, in both brands, with no hardcoded color. One screen in a real JIT app is now built with the kit too, a start and not coverage.

TL;DR

Instead of more documentation I gave assistants something to look up: tokens that name every color, size and font, a fact sheet per component, and a check that fails the moment anything drifts. Only one layer changes per brand, which is what makes a client project quick to start.

Context

JIT's internal apps grew over many years on different technologies with no shared source of truth, and now that they are moving into one place, every difference between them is something a user has to learn again. Then AI assistants started writing real screens: ask for a settings page and you get a good-looking one in a minute that belongs to no brand. Our small client projects have the same gap: no design system, a new brand each time, and screens built fast.

The problem

An AI assistant without a design system invents one. It made up button styles and names, and it hardcoded values: a raw color or number typed straight into the code, instead of the one the design system defines. It did all of this with total confidence.

Look at the image at the top. Both dialogs say the same words in the same font. The left one has no close button, a warning triangle where the kit uses an info circle, and every button grouped on the right. None of it fails a glance, which is why it slips through.

Coherence across the internal apps was the goal. AI made it urgent: the faster assistants get, the more a person has to find and fix. Client projects tested whether the answer was reusable, so a new brand had to be nearly frictionless.

What I noticed before building

  • A design decision is only real when it lives in exactly one place. Two editable copies of a color means the color has no owner.
  • An AI is most confident exactly when it is guessing. The fix is not better prose. It is giving it somewhere to look things up.
  • Documentation is only honest if it can fail. A wiki page goes stale silently. A playbook that gets run either works or breaks loudly.

What a design system needs when AI writes the screens

  1. Tokens in three layers. Each has a name and a purpose, and only the middle layer changes per brand.
  2. A base the assistant has seen. Built on shadcn, differences published.
  3. A fact sheet per component. What exists and what does not, generated from the code.
  4. A lookup. A connector the assistant calls mid-task.
  5. Judgment written down. Do and don't lists and playbooks.
  6. Drift that is loud. Shared names, one map between Figma and code, and a check that fails on any difference.

Assistants wrote most of the code. The seven decisions below, and the review of what they wrote, are mine. Decision one removes the hardcoding, and decision four the guessing.

Making the values real

Decision one: the tokens are the source of truth, and Figma is where designers edit them

Colors used to be copied by eye out of Figma, and every copy was a chance to drift. So I tokenized the kit: every color, and nearly every size, radius and font, is a named design token, and the components contain no raw colors.

A designer changes "primary" once, a skill (a playbook an assistant follows step by step) copies the change into the token file, and an automatic step writes the stylesheet. Nearly all 836 tokens carry a note on what they are for, so an assistant reads the intent, not just the value.

The trade-off: nobody can "just quickly fix a color in code" anymore. And the sync leans on an export tool I don't control. On one run it handed back old values in a changed format. I only noticed because I compared it with Figma itself, so I threw the export away and applied just the changes I could verify there.

Decision two: only one layer changes per brand, so a new brand is a column of values

Client projects keep arriving with a new brand and no design system, and a rebrand used to mean repainting every screen. So only the meaning layer changes per brand: switching between my two demo brands changes 61 of the 252 meaning values and none of the 277 component settings.

I tested that when I made the second brand denser, stepping every control down one rung. The change touched four token files and not one component. I kept the smallest button at 24 pixels, the minimum touch size in the accessibility guidelines, because a brand can be compact but not unusable.

The trade-off: a brand can change values but not the shape of a component. A client who wants a different button anatomy doesn't fit, and I scoped that out on purpose, because a change of shape is a design decision in Figma, not a special case in the code.

Decision three: build on shadcn, and publish every place the kit differs

An assistant that has never seen your component names will invent them, and mine did. So I built the kit on shadcn, a popular open source set of interface parts that nearly every AI model has already seen, and published every place the kit differs from it. There are eleven, and the first is buttons: ours has seven styles to shadcn's six, and secondary is our outline.

I checked the 45 components that have a shadcn twin against shadcn's live source. About half matched at first, and after one fix pass 36 did. The rest are differences I chose, each written down.

The trade-off: I gave up naming freedom and easy upgrades, because a snippet copied from shadcn's docs breaks in those eleven places. The list covers them.

Making the kit answerable

Decision four: let the kit answer questions instead of hoping it gets read

Documentation written for people goes stale silently, and an assistant that can't find an answer makes one up. So every component publishes a fact sheet generated from its code: its exact options, defaults, the tokens it uses and accessibility notes. A small connector, built on the Model Context Protocol (a standard way to plug tools into AI assistants), lets any assistant look those facts up in the middle of a task, so "Which button styles exist?" stopped being a memory test and became a lookup.

Facts can be extracted, but judgment can't. So one small folder is written by hand, so far for 16 of the 56 components: other names for a component ("modal" finds the dialog), do and don't lists, and when to use something else. Assistants may propose changes there and a person decides. The most useful lines say what does not exist, like an outline button, because that is exactly what an assistant would guess from shadcn.

The trade-off: component files follow a rigid pattern so the facts can be read straight from the code, and a few files are more awkward for it. I'd rather have a slightly awkward file than a fact sheet nobody can trust. I also kept the connector local on purpose, because a published copy could go stale: the same drift problem, one level up.

Decision five: Figma and code use the same names, and one map connects them

Figma and code were two vocabularies, and every translation was a chance to drift. So I made the names identical by rule, and one map ties each component's Figma node ID (the number Figma gives every layer) to its code file and key options.

The map keys on that ID and not on layer names, because the Figma file has duplicates. Figma's own tool for this needs a plan we don't have, so the map is a plain file that people and assistants can both read.

The trade-off: a map is only as true as its last check. Four node IDs went stale when the file moved to a new version, and a later sweep found a row that described something that never existed. So a playbook now resolves every ID against the live Figma file.

Making drift loud

Decision six: Storybook is where a designer checks the code against Figma

A designer shouldn't have to read code to check what got built. So every component has a Storybook story, a live page for trying it on its own, laid out like its Figma property panel, with the same names and options.

Figma draws every state, which is why the button is 280 variants there. In code, four of the five states come from the stylesheet and the fifth is one switch, disabled, so an assistant never has to choose a hover.

The trade-off: stories take longer to write this way, and one check is still missing. Storybook's accessibility check runs on every story, but I turned its contrast rule off because it raised false alarms when the brand flips. The Storybook is public, so you can try it yourself.

Decision seven: looks right is not right, so make drift loud

Fact sheets tell an assistant what is true. Something still has to catch it when it ignores them, or when anything else drifts. So every change rebuilds everything that is generated and compares it, character for character, with what is saved, and one drifted value turns the project red.

That check once caught an automated formatting pass that had quietly broken the fact sheets. I fenced those tools off from the generated files.

But a check only catches what it knows to look for, so I reviewed 53 components against their Figma versions and the rules of the kit. The rule I held hardest: a component that looks identical on screen still fails if it gets there with a raw color. Of the 53, 25 needed fixes.

A radio button's dot was hardcoded white. A switch's thumb was hardcoded white. A drawer's rounded corners resolved to the wrong radius. The output looked right and wasn't.

Recurring jobs became playbooks an assistant runs step by step: syncing tokens, adding a brand, auditing whether Figma and code still agree. A playbook either works or fails loudly, and the cost is the time to write them.

The outcome

The test that mattered: an empty project, an AI assistant connected to the kit, and one casual prompt, "build me a delete confirmation dialog". The assistant looked up the real component, used the destructive style, and produced a dialog that was on-brand in both brands, with no hardcoded color.

What I'd tell my past self

The audience of a design system now includes machines, and they need different things from people: facts they can look up, rules they can't misread, and a loud failure when something drifts. Designing for that changed what I count as good documentation.

Three things are still open. One screen in one JIT app is a start, not coverage. The sync should compare Figma with its own export instead of relying on me to notice. And nothing runs the Figma-side audit on a schedule yet, so a Figma change nobody syncs stays invisible until I look.
