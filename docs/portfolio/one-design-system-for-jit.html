One design system that designers, developers and AI assistants can all read

How do you make a family of internal apps feel like one product, when AI assistants now build a growing share of the screens?

Problem

JIT's internal apps and client projects have no shared design system to follow, so every screen, now often written by an AI assistant, invents its own colors and names.

Solution

Kraken is one design system that JIT's designers, developers and AI assistants all read from the same place: internal apps share one set of building blocks, assistants look things up instead of guessing, and a client project gets its own brand from a plain-language description.

TL;DR

JIT's apps look and behave like different products, and AI assistants building new screens were making that worse by inventing their own colors and names. I built a design system from an empty project: tokens in three layers where only one changes per brand, Storybook pages that mirror Figma, and seven skills that let an assistant look things up, sync tokens and add a brand. In tests, one casual sentence produced an on-brand dialog in both brands, and a plain-language brief became a working third brand in under three minutes with no component changes. I also designed a new screen each for Timeports and WeJit with the kit. It is an MVP: built and tested, not yet live in JIT's apps.

Context

Open two of JIT's internal apps side by side, like Timeports and WeJit, and they do not look like one product. The apps were built by different people, in different years, on different technologies, and they are moving into one place. At the same moment, AI assistants started writing real screens, and JIT's fixed-term client projects, where the client has no design system, each start from a blank page.

The problem

An assistant with no design system to follow invents one, and it does so with full confidence. It hardcodes colors, makes up option names, and produces screens that look fine alone and belong to no app. Every typed-in color is one more place that has to change the day the brand does.

What I noticed

Three things shaped everything I built after that:

  • A design choice is only owned when it lives in exactly one place. If the primary button's color can be edited in two places, nobody owns it.
  • An assistant is most confident when it is guessing. It states an invented button style as calmly as a real one, so better written guidelines would not fix it, it needed somewhere to look things up.
  • Documentation is only honest if it can fail. A wiki page goes stale without a sound, while a check that runs on every change turns red.

What I built

Decision one: every design choice is a token, in three layers, in one place

Problem. Figma, the code and the docs each held their own copy of every color, so they drifted apart quietly, and changing a brand meant touching every screen.

Solution. Every color, spacing and font is a token, kept in plain files in three layers: raw values, then meaning ("danger", "surface"), then the choices each component makes. Screens only use the component layer. The files are the truth, and Figma is the editor where a designer changes them.

How it worked. Because only the meaning layer changes between brands, a new brand never touches a component. The cost is that I cannot quickly fix a color in the code, and finding a real color takes two hops, which the component pages resolve for you.

This is also the decision I broke myself. I built a visual theme editor, pick a color and watch the whole kit restyle, and spent two weeks on it before I saw that it gave the tokens a second place to be edited. I deleted it, and theming moved fully into Figma.

Decision two: use the names the assistant already knows

Problem. An assistant that has to learn a new naming system will guess, and it guesses as confidently as it recalls.

Solution. I matched the names and options of shadcn, the open source set of interface parts that every major AI model has already seen. Where Figma genuinely differs, I kept Figma and published the difference in a short list: our buttons come in seven styles, not six, and "outline" does not exist because "secondary" is the outline.

How it worked. An assistant arrives with correct instincts and only has to learn the differences, not the whole system. The trade-off is naming freedom: I gave up names I would have preferred, and the list of differences has to be kept honest.

Decision three: make it AI native with skills and a lookup, and make any mismatch loud

Problem. Written guidelines cannot stop a model from guessing that a style called "outline" exists.

Solution. Every component has a fact sheet built straight from its code: its exact options, defaults and usage rules. A small tool lets an assistant ask for those facts in the middle of a task. The only part I write by hand is my judgment, for rules like "prefer a dialog unless the action is destructive".

Around that I wrote seven skills, step by step playbooks that an assistant follows instead of reinventing. They sync tokens from Figma, add a brand, add a component, build a component from its Figma design, check the map between Figma and code, audit for drift, and teach an assistant how to use the kit.

How it worked. Every change rebuilds the fact sheets and compares them with what is checked in, so one drifted value turns the project red until a person resolves it. It earned its place early: a formatting tool silently corrupted the sheets, the comparison caught it, and I fenced the tools that write content off from the tools that tidy it. I also kept the lookup tool on my own machine instead of publishing it, because a published copy can go stale against the live files, which is the same drift one step further out.

Storybook, docs and the map to Figma

When Figma and the code describe the same button in different words, someone ends up translating, and the translation is where mistakes start. So every component has a Storybook page, a place to try it out, with the same options and names as its Figma panel and a brand switch in the toolbar, and a map ties each Figma component to its code. Now a designer, a developer and an assistant all mean the same thing by "destructive button".

I documented the kit three ways: a user guide for anyone picking it up cold, a page for each of the 56 components that is built from the code so it cannot go stale, and a record of every decision with its trade-off. The hosted Storybook is open to try.

One design choice I kept from Figma on purpose is the Button. It has seven styles: four for ordinary actions (primary, secondary, tonal, ghost) and three destructive ones that mirror them, so even a delete gets the same strong, medium and quiet levels as every other action. Hover, focus and pressed looks are designed in Figma but live in the code as styling rules, so the only state a developer can set is disabled.

Adding a brand

A fixed-term client project has no design system, and a new brand should not mean a new codebase. Because only the meaning layer varies, adding a brand is three steps that a skill runs the same way every time.

I tested it with a made-up client and a one-line brief: "call the brand acme, make it lime green with display font mozilla text and secondary font inter". The assistant added the theme in Figma, pointing the brand colors at the lime ramp the kit already had, and set Mozilla Text for headings and Inter for body text. The Figma export did not list the new theme yet, so I wrote it into the token files from the live values and checked that the difference was only the new brand.

The result is a working third brand in under three minutes, measured from adding the theme to the first rendered screen. Of 252 meaning values, 36 changed, 20 colors and 16 fonts, no component file was touched, and the check passed with every component value unchanged. I then removed the test brand again.

The cost is that a brand which wants to change how a component is built, not just its values, does not fit this workflow, and I scoped that out on purpose. Acme also kept jit's corners and spacing, because the brief only asked for colors and fonts.

The outcome

The test that mattered was one casual prompt, "build me a delete confirmation dialog", given to the same assistant twice in an empty project: once with only our font, once with the kit connected. Without the kit, the assistant invented its own look. With it, the assistant found the right component, used the destructive style, and the dialog looked right in both brands with no hardcoded color.

That traces straight to the decisions: familiar names meant it started with the right instincts, the fact sheets meant it checked instead of guessing, and one layer per brand meant both brands came for free.

The second proof is two real apps, not only a demo. I redesigned a screen in Timeports, where people record their worktime, and a screen in WeJit, where colleagues find each other's profiles, with the kit. These are designs, not live yet.

The kit covers 56 components in two brands. This story covers building and testing the system and designing one screen in each of two apps. None of it is live in JIT's apps yet.

Reflection

My real job turned out to be deciding what was worth keeping, where truth was allowed to live, and what to delete. A system stays one system only if you refuse the shortcuts that look good in a demo, including your own.

This is an MVP. It has the basic building blocks, and bigger pieces made from them, like forms and whole page sections, come next, following atomic design.
