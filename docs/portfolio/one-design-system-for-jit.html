One design system that designers, developers and AI assistants can all read

How do you make a family of internal apps feel like one product, when AI assistants now build a growing share of the screens?

Problem

JIT's internal apps and client projects have no shared design system to follow, so every screen, now often built by an AI assistant, ends up with its own colors and names.

Solution

Kraken is one design system that JIT's designers, developers and AI assistants all read from the same place: internal apps share one set of building blocks, assistants look things up instead of guessing, and a client project gets its own brand from a plain-language description.

TL;DR

JIT's apps look and behave like different products, and AI assistants building new screens were making that worse by making up their own colors and names. I built a design system from an empty project: tokens in three layers where only one changes per brand, Storybook pages that mirror Figma, and seven skills that let an assistant look things up, sync tokens and add a brand. In tests, one casual sentence produced an on-brand dialog in both brands, and a plain-language brief became a working third brand with no component changes.

I also designed a new screen each for Timeports and WeJit with the kit. It is an MVP: built and tested, not yet live in JIT's apps.

Context

Open two of JIT's internal apps side by side, like Timeports and WeJit, and they do not look like one product. The apps were built by different people, in different years, on different technologies, and they are moving into one place. At the same time, AI assistants started writing real screens, and JIT's fixed-term client projects, where the client has no design system, each start from a blank page.

The problem

With no design system to follow, an assistant makes up its own. It types in colors by hand and invents option names, so each screen looks fine alone but does not match the app around it. Every hand-typed color is one more thing to fix when the brand changes.

What I noticed

Three observations shaped the rest of the work:

  • When the same color lived in two places, like Figma and the code, the copies slowly stopped matching, and nobody knew which one was right. Each design choice needed one home.
  • When an assistant did not know a value, it made one up: a hand-typed color, a button style that does not exist. Every app ended up a little different. The assistant needed somewhere to look things up.
  • A written guide goes out of date and nobody notices. A check that runs on every change fails as soon as the docs and the code stop matching.

What I built

Decision one: every design choice is a token, in three layers, in one place

Figma, the code and the docs each held their own copy of every color, so they drifted apart, and changing a brand meant touching every screen. So I made every color, spacing and font a token, kept in plain files in three layers: raw values, then meaning ("danger", "surface"), then the choices each component makes. Screens only use the component layer, the files are the truth, and Figma is the editor where a designer changes them.

Because only the meaning layer changes between brands, a new brand never touches a component. The cost is that nobody can quickly patch a color in the code, and finding the actual color means following two layers down, which the component pages do for you.

I broke this rule once myself. I spent two weeks on a visual theme editor, where you pick a color and watch the whole kit restyle, before I saw that it was a second place to edit the tokens. I deleted it, and theming moved fully into Figma.

Decision two: use the names the assistant already knows

An assistant that has to learn new names will guess, and you cannot tell its guesses from what it really knows. So I matched the names and options of shadcn, the open source set of interface parts that every major AI model has already seen. Where Figma differs, I kept Figma and published the difference in a short list: our buttons come in seven styles, not six, and "outline" does not exist because "secondary" is the outline.

An assistant already knows most of the names and only has to learn the differences. The cost is that I gave up some names I would have preferred, and the list of differences has to stay up to date.

Decision three: add a brand by describing it

A fixed-term client project has no design system of its own, and a new brand should not mean rebuilding the components. So I made adding a brand something you describe in plain words. A skill turns the description into a new theme in Figma, and because only the meaning layer changes, every component picks it up.

I tested it with a made-up client and a one-line brief: "call the brand acme, make it spacious and lime green, with darker grotesque and inter, and barely rounded corners". The assistant added the theme in Figma with a new lime color ramp and the two fonts. It set Darker Grotesque for headings and Inter for body text, made every spacing value larger and brought the corners down to 2 to 4 pixels, even on dialogs and cards. A second pass made it read less like jit: fainter divider lines, a lime tint on hover, pressed and focus states, and headings one size larger, because Darker Grotesque runs small. The Figma export did not list the new theme yet, so I wrote it into the token files from the live values and checked that the difference was only the new brand.

The result is a working third brand. Of the 252 meaning values, 93 changed: 26 colors, 20 spacing values, 6 corners, 3 shadows and 38 type settings (16 fonts, 10 weights, 7 sizes and 5 line heights). The raw layer gained 13 new values, the lime ramp and the two fonts, and none of the existing ones moved. No component file was touched, and the check passed with every component value unchanged.

The cost is that a brand which wants to change how a component is built, not just its values, does not fit this workflow, and I left that out on purpose.

Decision four: make the kit AI native, so assistants look things up instead of guessing

Written guidelines did not stop an assistant from guessing that a button style called "outline" exists. So I gave assistants the same facts people use, in a form they can read and ask questions of, and made every piece check itself.

  • Every component has a fact sheet built straight from its code: its exact options, defaults, tokens and usage rules. An index matches everyday words like "modal" or "toast" to the right component. The only part I write by hand is my judgment, for rules like "prefer a dialog unless the action is destructive".
  • A small lookup tool lets an assistant ask for a component, a token or a usage rule in the middle of a task, instead of reading the whole kit.
  • A map ties each Figma component to its code file and options by its Figma ID, so an assistant building from a Figma design lands on the right component, even when two Figma parts share a name.
  • The token files are the truth and Figma is where they get edited. A skill brings Figma edits back into the files as a change you can review, and a drift audit compares Figma, the token files and the code.
  • Components install with one command from a registry, the same way assistants already add shadcn parts.
  • A short instructions file at the top of the project tells any assistant where to start: read the rules first, never guess an option name, never edit the built files by hand.
  • Seven skills, step-by-step instructions an assistant follows instead of working things out from scratch each time. They sync tokens from Figma, add a brand, add a component, build a component from its Figma design, check the map between Figma and code, audit for drift, and teach an assistant how to use the kit.

Every change rebuilds the fact sheets and compares them with the saved ones, so one changed value fails the check until a person fixes it. Early on, a formatting tool silently broke the sheets, the check caught it, and I kept the tools that write content apart from the tools that tidy it.

I also kept the lookup tool on my own machine instead of publishing it. A published copy could fall behind the live files and give out old answers.

Storybook, docs and the map to Figma

When Figma and the code use different names for the same button, someone has to translate between them, and mistakes slip in. So every component has a Storybook page, a place to try it out, with the same options and names as its Figma panel and a brand switch in the toolbar. A map ties each Figma component to its code, so a designer, a developer and an assistant all mean the same thing by "destructive button".

I documented the kit three ways: a user guide for anyone picking it up cold, a page for each of the 56 components that is built from the code so it cannot go stale, and a record of every decision with its trade-off.

One design choice I kept from Figma on purpose is the Button. It has seven styles: four for ordinary actions (primary, secondary, tonal, ghost) and three destructive ones that mirror them, so even a delete gets the same strong, medium and quiet levels as every other action. Hover, focus and pressed looks are designed in Figma but live in the code as styling rules, so the only state a developer can set is disabled.

The outcome

The main test was one casual prompt, "build me a delete confirmation dialog", given to the same assistant twice in an empty project: once with only our font, once with the kit connected. Without the kit, the assistant invented its own look. With it, the assistant found the right component, used the destructive style, and the dialog looked right in both brands with no hardcoded color.

Three of the four decisions showed up in that one dialog. The familiar names gave the assistant a head start, the fact sheets and the lookup tool let it check instead of guess, and because only one layer changes per brand, the second brand needed no extra work.

I also used the kit on two real JIT apps. I redesigned one screen in Timeports, where people record their worktime, and one in WeJit, where colleagues find each other's profiles.

The kit covers 56 components in three brands. This story covers building and testing the system and designing one screen in each of two apps. None of it is live in JIT's apps yet.

Reflection

Most of my work turned out to be deciding what to keep, where each value should live, and what to delete. The hardest part was saying no to shortcuts that looked good in a demo, like my own theme editor.

This is an MVP with the basic building blocks. Bigger pieces built from them, like forms and whole page sections, come next, following atomic design.
